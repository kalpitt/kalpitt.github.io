How I build with AI

I build and run my products mostly with AI coding agents. Most of the work is setting up the rules, checks and notes around them.

Alongside my day job I build five products on my own: a toolkit for the Indian job switch, an offline anti-scam app for Android, a dictation app for Mac, a site of practical AI workflows, and Glass, a financial-analysis tool that's still being built. AI agents write most of the code. This page is about what I put around them so I can trust what they ship.

1 · Every repo has written rules

Each project has an operating manual (AGENTS.md) that every AI tool reads before it touches code. It says what the product is for, the rules that can never break, how the code is laid out, and what "done" means. Those rules are what make each product what it is: "the model never computes a financial number", "this app never touches the internet", "audio never leaves the Mac". Because the rules live in the repo, the work isn't stuck inside one chat or one tool.

2 · Automated checks hold the important rules

Agents forget instructions. Automated checks don't. So where a rule matters, a check enforces it:

  • Build checks (CI, the tests that run on every change) fail if the anti-scam app ever gains the internet permission, if an on-screen line is missing its Hindi version, or if a page on learnai.how drifts from the site template. This site has one too: it blocks publishing if a private file, a broken link or a false product claim would go live.
  • A grounding check in Glass rejects any model answer whose numbers don't trace back to a cited source, so an unsupported claim never reaches the screen.
  • Pre-action hooks warned an agent before it wrote a key into a normal file or committed straight to the main branch. They only ever caught typos, so I deleted them from four repos this autumn after six false alarms and no real catches.

3 · AI reviewers check the work

I use extra agents the way a good team uses senior reviewers. One checks every real change to Glass against its core rules. One reviews anything in the dictation app that touches permissions or how text gets typed. One turns news about scam-app campaigns into offline detection rules. One checks every claim about AI tools in a learnai.how article against a maintained list of facts. Reviewers only review: they report problems and leave the fix to the agent that wrote the change, and the final call to me.

4 · Notes that outlive the chat

  • Project notes: each repo keeps a current-state file and a short note at the end of every session, so the next agent, in any tool, starts where the last one stopped. Before work begins, the agent checks those notes against the git history.
  • Decision records: every hard-to-reverse choice is written down with its reasons. Agents read them before changing a core rule, and propose a new one for anything costly to undo. Only I accept them.

5 · Agents run on their own, up to a limit

Agents can work unsupervised on a branch under strict terms: one tested improvement per commit, no commit if a test fails, a log line for every change, and a stop after ten commits to write a report for me. In most repos only I can merge to main. In Switch Karle, an agent may merge its own change once every check passes, then must watch the deploy and roll it back if the live check fails. One overnight run made twelve tested improvements to the anti-scam app, each one logged and easy to review.

6 · The right model for each job

The most capable, most expensive models do the work where judgment matters: design, code that has to be trusted, long unsupervised runs. Cheaper models do well-specified work, because a detailed written spec plus tests that catch regressions makes the result predictable. I write those specs so the thinking is in the document, and any model can follow it.

7 · One week, every repo

In July 2026 I had a week of access to a top model and used it across every repo at once. The results:

  • A plan before code: for Glass, it read a real 140-page annual report and wrote a 700-line research plan, a decision record and a 14-task breakdown with a suggested model for each task. No code: the plan waited for my approval, and cheaper models build it afterwards.
  • A full unsupervised run: ten commits improved the dictation app's text clean-up, each tested and logged, then merged as one batch after I reviewed it.
  • Real detection, released: the anti-scam app gained three offline detection rules for 2026 scam-app campaigns, tested on an emulator and released as a signed v0.6.0.
  • The process itself: the rules, notes and model-routing policy were copied to every repo, and the best sessions became reusable templates.

The week ended with plans, decision records, releases and a process that cheaper models can keep using, rather than a pile of chat transcripts.

Why this matters at work

Companies adopting AI need the same things: rules enforced by checks rather than policy documents, a written record of decisions, a split between the AI that does the work and the AI or person that checks it, and human sign-off where the risk is. I run this every day on my own products, so I know what it takes to set it up for a team.
